# 迹觅·Evidence · 技术选型 PPT 语料（主要技术选型版）

> 用途：交给 GPT / PPT 生成工具，生成一份**只讲主要技术选型**的中文技术评审 PPT。
> 与 `docs/ppt_prompt.md` 的区别：本文件不展开作品背景、使用场景和未来路线，只回答“选了什么、为什么选、代价是什么”。
> 原则：只引用本文件的事实；不编造数字；不暴露 API Key、内部地址、客户数据；不写“100%”“完全替代人工”。

---

## 一、可直接粘贴的 Prompt

你是技术方案 PPT 撰稿人。请基于下方技术事实，生成一份 **8–9 页**的中文技术选型 PPT。

要求：

1. 每一页围绕一个主要技术层，结构统一为：**选型 → 为什么选 → 代价/边界**；
2. 先给结论，再给论据；不要堆砌库名和版本号；
3. 可用对比表、分层架构图、选型取舍矩阵、证据链示意；
4. 每页输出：页面标题、核心结论（一句话）、3–5 条要点、可视化建议、演讲备注；
5. 只讲主要技术选型，不展开业务背景、使用场景和未来路线图；
6. “自学习”必须写成**检索式案例记忆 + Beta 反馈加权**，不是模型微调，也不自动改规则/阈值；
7. 不出现任何密钥、内部服务地址、客户隐私；不使用“100%”“完全替代人工”等表述。

## 二、一句话总览

用 **FastAPI + LangGraph** 做可控的多阶段 Agent 编排，用 **SQLite + Chroma/BGE/BM25** 做可审计的数据与混合检索，用 **DeepSeek / Qwen / Sightengine / Tavily** 做分工取证，用 **规则 + 语义余弦** 把大多数消息挡在零 token 的触发层，用 **Vue + SSE** 做可观测，最后用**人工复核 + 检索式案例记忆 + Beta 反馈**把经验回流。

|---|---|---|---|

## 四、逐项选型说明

### 1. 后端：Python 3.13 + FastAPI + Pydantic v2

**选型**

- Python 3.13；
- FastAPI + Pydantic v2 + pydantic-settings；
- uvicorn 单 worker；
- OpenAPI/Swagger 自动生成接口文档。

**为什么**

- 分析链路大量是异步 IO：LLM、识图、Sightengine、Tavily、SSE，FastAPI 的 async 模型合适；
- Pydantic v2 同时承担请求校验、响应 schema、配置管理，减少重复代码；
- Swagger 让对外接口、管理接口、演示接口可独立验证，便于联调；
- Python 生态与 LangGraph、Chroma、fastembed、jieba 等 AI 组件衔接成本最低。

**代价/边界**

- 单 worker 是为了配合进程内 EventBus；横向扩展需要改为外部队列/消息总线；
- Python 的 CPU 密集任务不适合放在事件循环里，向量推理统一放线程池；
- 当前是单机部署，不追求多租户与高并发。

**备选与取舍**

- Node/Go 后端：生态与 AI 组件衔接弱，团队迭代成本更高；
- Django：更重，SSE/异步 Agent 场景不需要其 ORM 全家桶；
- 多 worker：会破坏进程内事件总线，当前阶段不采用。

---

### 2. Agent 编排：LangGraph + ReAct 子代理

**选型**

- LangGraph `StateGraph` 做确定性流水线；
- 一个 ReAct 调查子代理按需调用工具；
- 节点级事件、条件回边、预算闸门。

**流水线**

```text
案件准备 → 场景路由 → 本地取证 → AI 生成预检
→ 知识库召回 → 先前案例召回 → 视觉定位
→ 调查 Agent → 一致性核对 → 裁决
→ 报告 → 收尾
```

裁决证据不足时可回到调查节点，最多 2 轮。

**为什么**

- 反欺诈需要**可控、可审计**的流程，而不是让模型自由发挥；
- LangGraph 把“先取证、再调查、再裁决”的步骤显式化，每个节点都能发事件；
- 只有调查阶段用 ReAct，工具调用范围可控，成本和风险都更低；
- 条件回边让“证据不足再查一轮”成为图上的显式逻辑，而不是藏在提示词里。

**代价/边界**

- 引入 LangGraph 依赖，节点状态需要设计；
- 不是“多智能体自由协作”，而是一条确定性主链 + 一个受控子代理；
- 复杂分支会增加调试成本，因此保持节点数量克制。

**备选与取舍**

- 纯提示词链：不可观测、难回放；
- AutoGen/CrewAI 等自由多智能体：可控性和成本不如显式图；
- 自研编排：短期可行，长期维护成本高。

### 3. 数据与检索：SQLite + Chroma + BGE + BM25 + RRF

**选型**

- SQLite（aiosqlite，WAL，外键开启，应用层单写锁，版本化迁移）作为唯一事实源；
- Chroma 持久化向量；
- `BAAI/bge-small-zh-v1.5`，fastembed / ONNX，CPU 推理，免 torch；
- jieba + BM25Plus 做关键词检索；
- RRF 融合（k=60，dense 权重 1.0，BM25 权重 0.8）；
- doctrine 知识库与先前案例使用**独立集合**：`kb_chunks` / `prior_case_chunks`；
- 向量模型或 Chroma 不可用时自动降级为 BM25-only。

**为什么**

- 运行、事件、报告、复核、案例、反馈都需要事务与可追溯，SQLite 足够且零运维；
- 中文客服短句里，纯向量容易漏关键词，纯 BM25 容易漏同义表达，混合检索更稳；
- BGE-small-zh 体积小、中文效果好、CPU 可跑，适合本地与低成本部署；
- RRF 不依赖分数尺度，便于融合两路异构检索；
- 独立集合避免先前案例与 doctrine 互相污染，删除/重建先例不影响知识库；
- 失败时降级而不是让服务挂掉，符合可观测系统的可用性要求。

**代价/边界**

- SQLite 单写锁不适合高并发写入和多节点；
- Chroma 是本地索引，不是分布式向量库；
- 本地小模型的上限低于大型云端 embedding；
- 索引需要重建/维护，删除案例要同步清理 Chroma 与 BM25。

**备选与取舍**

- PostgreSQL/MySQL：当前单机规模不需要，后续可迁移；
- Redis/Celery：当前单 worker 不需要队列；
- 云端向量库/大 embedding：成本、延迟、数据边界不合适；
- 纯 BM25 或纯向量：单独一路都不够稳。

### 4. 模型与第三方：分工而不是“一个大模型包打天下”

**选型**

| 角色 | 选型 | 用途 |
|---|---|---|
| 主推理 | DeepSeek Flash | 调查、裁决、人工复核对话、案例生成 |
| 识图 | Qwen3.7-Flash | 图片分区、单据字段、篡改定位、诉求相关性 |
| AI 生成预检 | Sightengine `genai` | 检测不可见水印/模型指纹，给识图提供定位线索 |
| 联网 | Tavily | 按需核实外部事实 |

**关键设计**

- 所有图片先过 Sightengine；**≥0.90 才纳入 AI 生成考量，≥0.95 才触发“不得判真实，至少疑似欺诈”的裁决硬约束**；
- 高分不等于定罪：必须由 Qwen 定位篡改区域，并判断与客户诉求的关系（related / unrelated / uncertain）；
- related 才支持欺诈；unrelated 且诉求区域真实时可按真实性判断；uncertain 不得直接定罪；
- 模型调用有独立预算：LLM 次数、工具次数、识图次数、联网次数、prompt token、单次运行成本；
- 识图与 Sightengine 结果按图持久缓存，跨运行复用。

**为什么**

- 主推理、视觉、硬信号、联网是四种不同能力，单模型很难同时做到成本、中文、可解释；
- DeepSeek Flash 适合中文推理与低成本高频调用；
- Qwen 中文识图与 DashScope 兼容接口接入成本低；
- Sightengine 补足“看不见的水印/模型指纹”，与可见痕迹分析互补；
- Tavily 只在需要外部事实时调用，避免无意义联网。

**代价/边界**

- 多一个外部服务就多一个延迟、失败点和费用项；
- 第三方分数有误报，必须结合定位与诉求相关性，不能单独定罪；
- 不同模型的输出格式需要统一和校验；
- 外部 API 需要在 `.env` 管理密钥，前端不接触密钥。

**备选与取舍**

- 全部用 GPT-4o/Claude：成本更高，且单一模型仍无法覆盖不可见水印；
- 纯本地 VLM：当前硬件与效果不匹配；
- 规则直接判图：无法处理复杂视觉语义。

### 5. 触发层：规则 + 语义余弦，零 LLM

**选型**

- `rules.yaml` 维护关键词、正则、图片条件、渠道条件和语义锚点；
- 语义命中用同一个 BGE 模型：
  - 客户原文按标点切子句，最多 8 条；
  - 锚点短语按 document 编码，客户子句按 query 编码；
  - 每个锚点组取“子句 × 锚点”的最大余弦；
  - 过阈值后参与 `any_semantic` 规则；
- 锚点组：退款意图、商品损坏、医疗索赔、种草意图；
- 阈值按组标定（约 0.66–0.70），命中等级分“完全命中 / 疑似 / 普通”；
- 触发阶段不调用 LLM。

**为什么**

- 大多数消息不需要分析，先挡掉可以显著降成本、降延迟；
- 关键词规则可解释、可审计，语义余弦补足同义表达；
- 规则与语义都在本地完成，触发阶段零 token；
- 阈值与锚点可以在规则页调整并热重载，不需要改代码。

**代价/边界**

- 阈值和锚点需要持续标定，存在误报/漏报；
- 语义模型不可用时自动降级为纯关键词；
- “完全命中/疑似/普通”是匹配强度，不是案件风险，展示时必须区分。

**备选与取舍**

- 每条消息都过 LLM 分类：成本与延迟不可接受；
- 纯关键词：中文表达变化多，漏报明显；
- 纯语义：短句和领域词容易漂移，规则仍需要兜底。

### 6. 前端与可观测：Vue 3 + Vite + TS + Tailwind + SSE

**选型**

- Vue 3 + Vite + TypeScript + Tailwind 4；
- 管理观测台：深色运维台，Axios + ECharts + marked；
- 演示客服台：白底 + 少量紫色，独立前端与独立后端；
- SSE 事件流：事件信封、单调 `seq`、`Last-Event-ID` 断线续传；
- 后端先落库再发布事件，SSE 连接先订阅再回放 DB；
- 模型输出按字段渲染，不直接铺原始 JSON。

**为什么**

- Vue 3 组合式 API 与 TypeScript 适合快速搭复杂运维界面；
- Vite 启动与构建快，Tailwind 让深浅两套视觉快速落地；
- SSE 对“服务端单向推送运行事件”足够，浏览器原生支持、断线重连简单；
- 事件先落库再发布，刷新/重连后可以从 DB 回放，保证观测不丢；
- 管理台与演示台分离，演示台只通过对外 API 接入，能证明“真实外部平台”的接入方式。

**代价/边界**

- SSE 是单向的，人工操作仍走普通 POST；
- 进程内 EventBus 要求单 worker，不能直接多副本；
- 两套前端增加维护面，但换来管理/演示边界清晰；
- 事件量大时需要前端折叠与分页，不能全部铺开。

**备选与取舍**

- React：同样可行，当前团队与项目迭代选择 Vue；
- WebSocket：双向能力当前用不上，SSE 更简单；
- 单前端：管理接口与演示接口混在一起，不利于证明外部接入边界。

### 7. 人工在环与自学习：检索式案例记忆 + Beta 反馈

**选型**

- 人工复核：欺诈 / 真实 / 证据不足三种终局判决；
- 复核 Agent 最多 4 轮追问，也可以零追问；追问与案例文档流式输出；
- 案例文档写入独立先前案例库，进入独立 Chroma + BM25 索引；
- 后续分析召回先例，作为证据链中的参考证据；
- Beta(2,2) 先验：采纳 +1α、推翻 +1β；可靠性 = α/(α+β)；
- 只处理被本案裁决引用的先例；不适用不降权，中性不改权重；
- 先前案例支持删除，删除时同步清理索引，来源复核回到可重新生成。

**为什么**

- 反欺诈是高风险决策，必须保留人工最终判断；
- 案例文档比“模型参数”更可审计、可回滚、可解释；
- 检索式记忆不需要微调，数据量小也能生效；
- Beta 后验让“被采纳/被推翻”的历史影响后续排序与证据权重；
- 只对被引用先例回写，避免无关案例被误更新。

**代价/边界**

- 自学习是**检索增强**，不是模型微调，也不会自动改规则/阈值；
- 依赖复核质量；复核草率会污染先例；
- 先例只是参照，裁决必须比较相似点/差异，不能照搬；
- 案例删除/重建需要同步维护索引。

**备选与取舍**

- 微调模型：数据少、成本高、不可解释、难回滚；
- 自动改规则/阈值：风险不可控，不符合人工授权边界；
- 只存不复用：人工经验仍然是黑箱。

## 六、未采用 / 暂不采用

| 方案 | 当前不采用的原因 | 何时再考虑 |
|---|---|---|
| PostgreSQL / MySQL | 单机单 worker，SQLite 足够且零运维 | 多节点、高并发写入 |
| Redis / Celery / 消息队列 | 当前运行量不需要异步队列 | 多 worker、长任务解耦 |
| 云端向量库 / 大 embedding | 成本、延迟、数据边界不合适 | 数据规模或跨地域检索上来 |
| 单一 GPT-4V/Claude 包打天下 | 成本高，且无法覆盖不可见水印 | 预算充足且需要统一模型 |
| 每条消息 LLM 分类 | 成本/延迟不可接受 | 触发准确率成为主要瓶颈 |
| WebSocket | 当前只需服务端单向事件推送 | 需要双向实时协作 |
| 微调 / 自动改规则 | 数据少、不可解释、风险高 | 有大规模标注与治理机制 |
| 微服务拆分 | 当前团队与流量不需要 | 多团队独立部署、独立扩缩容 |

## 七、答辩口径（可选）

**Q：为什么不用一个大模型直接判？**
A：成本、延迟、可解释性都不合适。触发层先用规则 + 语义余弦挡掉大多数消息；只有需要分析的案件才进入多阶段 Agent，且不同模型按能力分工。

**Q：为什么用 SQLite，不用 PostgreSQL？**
A：当前是单机单 worker，SQLite 的 WAL、事务和迁移足够，且零运维；代价是不适合高并发和多节点，后续可以迁移。

**Q：为什么自学习不微调？**
A：数据量小、风险高、不可解释。我们用“人工判决 → 案例文档 → 独立检索 → 先例证据 → Beta 反馈”的检索式记忆，可审计、可回滚，不自动改规则。

**Q：为什么 SSE，不用 WebSocket？**
A：运行事件是服务端到客户端的单向流，SSE 更简单，浏览器原生支持，断线用 Last-Event-ID 续传；人工操作仍走 POST。

**Q：为什么 Sightengine 高分还不能直接定罪？**
A：它检测的是不可见水印/模型指纹，不指出篡改位置。必须由识图模型定位篡改区域，并判断是否与客户诉求相关；只有相关才支持欺诈，无法定位时至少疑似并转人工。

## 八、事实边界

- 后端测试：127 个通过；ruff 通过；两端前端 `vue-tsc` + Vite 构建通过。
- 单 worker 是当前部署约束，不是永久架构结论。
